# 设计取舍记录（ADR）

格式：**背景 → 决策 → 后果 → 被否掉的方案**。只记录"会影响以后怎么改代码"的决策。

---

## ADR-001 履约用编排式 Saga，而不是 2PC 或纯协同

**背景**：一笔订单要跨库存、支付、出库三个参与方，且失败必须可回滚。

**决策**：由 `SagaOrchestrator` 显式驱动步骤，步骤状态落在 `saga_steps` 表。

**后果**：流程可追踪、可重放、崩溃可接管；代价是编排器成为核心组件，且补偿逻辑必须逐个实现。
业务接受"最终一致"，用户可能短暂看到 `STOCK_RESERVED`。

**否掉**：
- 2PC：需要参与方支持准备阶段，长时间持锁，协调者单点。
- 纯事件协同：3 个参与方时链路还能读，但"卡住之后谁负责"变成隐式的，排障成本高。

## ADR-002 事件用事务性 Outbox，不用双写或 CDC

**背景**：状态变更要通知读模型/通知服务，但不能出现"订单改了事件丢了"。

**决策**：业务写入与 `outbox` 记录在同一事务提交，由中继轮询投递。

**后果**：最多延迟一个轮询周期（默认 300ms）；需要一张表和清理策略；投递语义是至少一次。

**否掉**：
- 应用内双写（先写库再发消息）：中间崩溃就丢事件。
- CDC（Debezium）：需要额外组件与 binlog 权限，本地演示不划算。
- 直接同步调用消费者：把下游故障引入主链路。

---

## ADR-003 投递语义选"至少一次 + 消费幂等"

**背景**：分布式下"恰好一次"需要两阶段确认，成本高。

**决策**：`processed_events(consumer, event_id)` 主键占位，消费者处理前先占位。

**后果**：消费逻辑必须可重入（本项目消费者都是 append 投影，天然幂等）。
不同消费者的进度可以不一致；事件在全部消费者完成后才置为 `PUBLISHED`。

**否掉**：追求恰好一次 → 需要分布式事务或去重窗口的精确水位管理，收益不匹配。

## ADR-004 并发控制用条件 UPDATE + 租约，不用悲观锁/Redis 锁

**背景**：库存不能超卖；同一订单不能被两个执行器同时推进。

**决策**：
- 库存：`UPDATE ... WHERE on_hand - reserved >= :qty`，rowcount 判定。
- 订单：`saga_owner + saga_lease_until` 条件更新领取，过期可抢占。

**后果**：不依赖 `SELECT FOR UPDATE`（SQLite 没有），同一套代码在 Postgres 下语义一致；
租约需要选一个合适的过期时间（默认 5s），过短会导致重复执行（支付幂等兜底），过长则恢复变慢。

**否掉**：
- 悲观行锁：SQLite 不支持，且长事务会拖住整个库。
- Redis 分布式锁：引入外部依赖；锁与业务数据不在同一事务里，仍有"锁住了但事务回滚"的窗口。

## ADR-005 库存预留必须有 TTL，并配主动回收

**背景**：库存是最贵的资源，用户下单不付款会把货锁死。

**决策**：预留记录带 `expires_at`；恢复器扫描到期预留并触发补偿（`RESERVATION_EXPIRED`）。

**后果**：需要后台扫描（默认 1s 一次）；TTL 是业务参数（默认 90s），过短会误杀正常支付。

**否掉**：只在用户主动取消时释放 —— 现实里用户不会取消，只会离开。

## ADR-006 支付超时判为"未确认"，不判失败也不判成功

**背景**：网关超时时，钱可能已经扣了。

**决策**：超时记录为 `DECLINED` + 明确错误信息，走退避重试；重试耗尽才补偿。
`provider_ref` 由订单号确定性派生，重试不会二次扣款。

**后果**：极端情况下会出现"钱扣了但订单取消"的窗口，真实系统需要**查询接口对账**来收敛（本项目未实现，已在局限中标注）。

**否掉**：超时即失败 → 用户被扣款但订单取消，是最糟的用户体验。

## ADR-007 默认 SQLite，但不在业务代码里写 SQLite 方言

**背景**：要求"克隆即可运行"，但也希望以后能换 Postgres。

**决策**：`Database` 封装引擎与 PRAGMA（WAL / busy_timeout），服务层只用 SQLAlchemy 表达式 + 条件更新。

**后果**：单机零依赖启动；但 SQLite 单写者导致写吞吐受限（实测约 22 单/s，见 README 容量分析）。
`run_in_tx` 统一处理锁冲突重试，把差异收在一处。

**否掉**：一上来就要求 Postgres + Docker —— 提高复现门槛，而演示价值主要在校验机制而非压测数字。

## ADR-008 缓存与限流先做进程内实现，并明确单实例假设

**背景**：库存读路径读多写少；同时需要防止单机被打穿。

**决策**：`TTLCache`（写后主动失效）+ `TokenBucket`（按 API Key/IP 分桶），均为线程安全的内存实现。

**后果**：零依赖、低延迟；**多实例部署时失效不跨进程、限流不全局**。已在 README 局限中写明，
并把接口设计成可替换（`invalidate/invalidate_prefix`、`check(key)`）。

**否掉**：直接引入 Redis —— 对一个单进程演示项目是过度设计，且会掩盖"为什么需要它"的判断过程。

## ADR-009 价格与商品信息一律服务端决定

**背景**：客户端传来的单价不可信（改价下单是最常见的资损漏洞之一）。

**决策**：下单请求只接受 `{sku, quantity}`，价格在下单时从 `products` 读取并写入 `order_items` 快照。

**后果**：SKU 不存在直接 404；商品调价不影响历史订单金额（快照语义）。

**否掉**：信任客户端金额 + 服务端校验 —— 校验逻辑容易漏，且历史订单金额会随调价漂移。

## ADR-010 指标自研轻量注册表，而不是引入 prometheus_client

**背景**：只需要 counter/gauge/histogram 三种原语。

**决策**：`obs/metrics.py` 约 130 行，输出标准 Prometheus 文本格式。

**后果**：无额外依赖、埋点代码在评审里可见；但只支持进程内指标，多 worker 需要 multiprocess 模式或 sidecar 聚合。
库层面的积压（`outbox_pending` 等）在 `/metrics` 请求时实时查库补齐，避免维护内存镜像导致漂移。

**否掉**：prometheus_client —— 依赖不大，但会让人误以为多进程指标已经解决。
